# Knowledge Structure Mapping｜层级构建核心参考

> 状态：Canonical Operational Reference（规范操作参考）
> 用途：作为 `skills/knowledge-structure-mapping/SKILL.md` 的唯一高浓度知识参考。
> 边界：用于判断大多数常见知识层级、概念关系、研究地图、产品模型与 Agent / Skill 架构；不追求集合论、格论、FCA 或本体工程的理论穷尽。
> 来源基础：本目录 `01_知识结构梳理的形式基础.md`、`02_结构关系词表与判定规则.md`。本文件负责操作语义与判定规则；前两份保留研究依据与扩展说明。

---

## 1. 核心原则

**Semantics first, representation second（先语义，后表示）。**

知识结构构建的顺序是：

```text
Modeling Purpose（建模目的）
→ Node Extraction（节点提取）
→ Node Typing（节点定型）
→ Relation Typing（关系定型）
→ Sibling / Axis / Partition Checks
→ Partial-order Checks
→ Structure Representation
→ Current-node Localization
→ Unknown / Conflict Marking
```

禁止先画 Tree（树）再强行寻找父子关系。

---

## 2. Modeling Purpose（建模目的）

Node Type（节点类型）与 Relation Type（关系类型）依赖当前模型。

同一个词可以在不同任务中承担不同结构角色。

例：

```text
“程序员”
人物档案：职业 = 程序员
→ Value（取值）

职业分类：程序员 / 医生 / 教师
→ Class / Concept（类 / 概念）
```

**规则：** 判断结构角色，不判断词典词性。

---

## 3. Node Extraction（节点提取）

### 3.1 Working Definition（项目工作定义）

**Node（节点）**：在当前建模目的下，需要被独立指认、重复引用，并与其他对象建立关系的语义单元。

Node Extraction 不是名词抽取。

### 3.2 三个检查

- **Identity（可指认性）**：是否存在稳定可引用的对象 / 概念？
- **Relationality（可关系化）**：是否需要与其他节点建立一个或多个关系？
- **Granularity（粒度）**：当前问题下是否过粗或过细？

### 3.3 Implicit Node（隐含节点）

文本未显式出现、但为了表达结构必须补出的节点可以加入，但应标记为推断或工作节点，不得伪装成原文显式事实。

---

## 4. Canonical Working Node Types（规范工作节点类型）

> 这是本项目的操作型 node-role vocabulary（节点角色词表），不是声称穷尽所有本体类型。

| Node Type | 精确定义 | 典型判断 |
|---|---|---|
| **Instance（实例）** | 一个具体、可指认的对象或个案 | “这是某一类中的一个具体成员吗？” |
| **Class / Concept（类 / 概念）** | 一类对象或一个一般抽象概念 | “这是某一类事物 / 概念本身吗？” |
| **Dimension / Facet（维度 / 分面）** | 描述对象或模型的一条独立观察轴 | “我们在描述哪个方面？” |
| **Value（取值）** | 某个 Dimension 上的具体状态、类别或值 | “这个方面当前是什么？” |
| **Component（组成部分）** | 某个整体内部的组成单元 | “这是整体的一部分吗？” |
| **Process / Stage（过程 / 阶段）** | 一个过程本身或流程中的阶段 / 事件化步骤 | “当前模型是在描述发生顺序或过程吗？” |
| **Relation（关系）** | 连接节点的谓词；仅在关系本身成为分析对象时将其 reify（实体化）为节点 | 默认优先作为 edge（边），而非普通节点 |

### 4.1 Dimension vs Value

```text
年龄 → Dimension
22岁 → Value

Cost → Dimension
High Cost → Value

Relative Effect → Dimension
Advantage → Value
```

### 4.2 Instance vs Class

```text
林凡 → Instance
主角 → Class / Concept

某一部具体重生短剧 → Instance
重生题材 → Class / Concept
```

## 5. Canonical Relation Types（规范关系类型）

### 5.1 INSTANCE_OF（实例属于类）

形式直觉：`x ∈ A`

```text
某作品 → INSTANCE_OF → 重生短剧
林凡 → INSTANCE_OF → 主角
```

测试：左侧是否是右侧类别中的一个具体实例？

---

### 5.2 IS_A / SUBCLASS_OF（是一种 / 子类）

形式直觉：`A ⊆ B`

```text
Information Advantage → IS_A → Advantage
金毛犬 → IS_A → 狗
```

测试：任何 A 在定义上是否都应是 B？

**警告：** 当前实例恰好全部落入 B，不足以单独证明 IS_A。

---

### 5.3 PART_OF（部分—整体）

```text
车轮 → PART_OF → 汽车
资产抽取模块 → PART_OF → 影视生产工作流
```

测试：A 是 B 的组成部分，而不是一种 B 吗？

**PART_OF ≠ IS_A**

---

### 5.4 VALUE_OF（取值属于维度）

```text
Advantage → VALUE_OF → Relative Effect
High Cost → VALUE_OF → Cost
Relationship → VALUE_OF → Locus
```

测试：A 是否是 B 这一 Dimension 上的一个 Value？

---

### 5.5 FACET_OF / DIMENSION_OF（维度属于模型）

```text
Relative Effect → FACET_OF → Premise Architecture
Cost → FACET_OF → Advantage Architecture
Locus → FACET_OF → Premise Architecture
```

测试：A 是否是描述 B 的一条独立观察轴？

---

### 5.6 BROADER / NARROWER（概念广狭）

用于存在语义广狭关系、但不准备声明严格 SUBCLASS_OF 的场景。

按 SKOS 方向：

```text
较窄概念 → BROADER → 较广概念
较广概念 → NARROWER → 较窄概念
```

例：

```text
修仙题材 → BROADER → 奇幻题材
奇幻题材 → NARROWER → 修仙题材
```

**BROADER / NARROWER 比 IS_A 的语义承诺更弱。**

---

### 5.7 ASSOCIATED_WITH（关联）

用于稳定相关、但不存在更强的上下位、部分整体、分面、顺序或机制关系。

```text
Suspense ↔ ASSOCIATED_WITH ↔ Curiosity
```

**Strong relation（强相关） ≠ Hierarchy（层级）。**

---

### 5.8 PRECEDES（先于）

只表示 temporal / procedural order（时间 / 流程顺序）。

```text
Premise Analysis → PRECEDES → Plot Analysis
```

**PRECEDES ≠ Parent / PART_OF / CAUSES**

---

### 5.9 CAUSES / ENABLES / CONSTRAINS（机制关系）

#### CAUSES（导致）

A 的变化导致 B 发生。

```text
A → CAUSES → B
```

#### ENABLES（使能）

A 让 B 成为可能，但 A 本身未必足以保证 B 发生。

```text
Information Asymmetry → ENABLES → Dramatic Irony
```

#### CONSTRAINS（约束）

A 限制 B 的可选范围、状态空间或行动方式。

```text
Budget → CONSTRAINS → Production Choices
```

压缩：

```text
CAUSES      = 让 B 发生
ENABLES     = 让 B 可以发生
CONSTRAINS  = 限制 B 可以怎样发生
```

---

### 5.10 EQUIVALENT_TO / SAME_AS（等价 / 同一）

仅在两个节点真正等价或指向同一对象时使用。

以下均不足以推出等价：

- 高度相似；
- 经常一起出现；
- 当前案例中功能相近；
- 当前 extension（外延）恰好相同。

```text
Similarity ≠ Equivalence
Association ≠ Equivalence
Same current extension ≠ Same concept
```

## 6. Relation Families（关系家族）

| Family | Relation Types |
|---|---|
| Instantiation（实例化） | INSTANCE_OF |
| Taxonomic / Hierarchical（分类 / 层级） | IS_A, BROADER / NARROWER |
| Mereological（部分—整体） | PART_OF |
| Faceted（分面） | VALUE_OF, FACET_OF |
| Associative（关联） | ASSOCIATED_WITH |
| Temporal / Procedural（时间 / 流程） | PRECEDES |
| Mechanistic（机制） | CAUSES, ENABLES, CONSTRAINS |
| Equivalence（等价） | EQUIVALENT_TO / SAME_AS |

## 7. Sibling Check（同级检查）

输出：

```text
Parent
├─ A
├─ B
└─ C
```

前，检查：

### 7.1 Criterion（划分标准）

A / B / C 是否回答同一个问题？

### 7.2 Node Type

A / B / C 是否承担同一种 Node Type？

### 7.3 Relation Type

A / B / C 与 Parent 是否使用同一种 Relation Type？

### 7.4 Overlap（重叠）

是否允许同一对象同时落入多个 sibling？

Overlap 不自动构成错误；必须与建模目的一致。

### 7.5 Exhaustiveness（穷尽）

是否声称 siblings 已经覆盖完整空间？

如果未验证，不要暗示“只有这些类型”。

### 7.6 Sibling Gate

```text
同轴
+ 同型
+ 同边
+ 重叠明确
+ 穷尽慎言
```

---

## 8. Single-axis Check（单轴检查）

不同 Facet 的 Values 不能直接作为同一组 siblings。

错误：

```text
Premise Architecture
├─ Advantage
├─ Transformation
└─ Relationship
```

正确语义：

```text
Advantage      → VALUE_OF → Relative Effect
Transformation → VALUE_OF → Operation
Relationship   → VALUE_OF → Locus
```

因此三者属于不同轴。

---

## 9. Partition Claim Check（划分声明检查）

严格 Partition（划分）要求：

- **Pairwise Disjoint（两两不重叠）**
- **Collectively Exhaustive（合起来穷尽）**

```text
“常见类型包括 A / B / C”
≠
“X 只能分成 A / B / C，且三类互斥”
```

Taxonomy（分类体系）不自动等于严格 Partition。

---

## 10. Partial Order（偏序）与 Hierarchy

只对**同一种 relation**检查 order properties。

### 10.1 Reflexive（自反）

`A ≤ A`

通常不在可视化中绘制自环。

### 10.2 Antisymmetric（反对称）

```text
A ≤ B
B ≤ A
⇒ A = B
```

若不同概念形成双向 hierarchy，检查：

- equivalence / duplicate concept；
- Relation Type 是否错误；
- hierarchy 是否存在冲突。

### 10.3 Transitive（传递）

```text
A ≤ B
B ≤ C
⇒ A ≤ C
```

祖先关系通常可由传递性推导。

---

## 11. Incomparability（不可比较）

同一个 hierarchy 内，两个节点可以没有上下关系。

```text
狗 IS_A 动物
猫 IS_A 动物

狗 与 猫
→ 在 IS_A order 中不可比较
```

**Incomparable ≠ Different Facets**

- 狗 / 猫：同一 relation system 内不可比较；
- Advantage / Relationship：首先属于不同 Facet，不应当作同一偏序中的 ordinary incomparable pair。

---

## 12. Multiple Parents（多父节点）

如果同一种 hierarchy relation 下：

```text
C IS_A A
C IS_A B
```

C 可以拥有多个 direct parents（直接上位）。

这不是 Tree，而应使用 DAG。

**不同 Relation Type 或不同 Facet 不构成 multiple inheritance。**

---

## 13. Cycle（环）检查

若：

```text
A IS_A B
B IS_A C
C IS_A A
```

且 A / B / C 被视为不同概念，则通常存在结构冲突。

优先检查：

1. 是否实际等价；
2. Relation Type 是否误判；
3. 是否存在重复节点；
4. hierarchy 是否错误。

---

## 14. Direct Parent / Ancestor 与 Hasse 思维

```text
金毛犬 → 狗 → 哺乳动物 → 动物
```

对于金毛犬：

- Direct Parent：狗
- Ancestors：狗、哺乳动物、动物

若 `A → B → C` 且传递性可推出 `A → C`，默认只保留 direct / cover relations：

```text
显示：
A → B
B → C

省略可推导：
A → C
```

目的：减少结构噪音。

---

## 15. Structure Representation（结构表示）

### 15.1 Tree（树）

适用：

- 主要是同一种 hierarchy relation；
- 每个非根节点只有一个 direct parent。

### 15.2 DAG（Directed Acyclic Graph，有向无环图）

适用：

- 主要仍是同一种 hierarchy relation；
- 允许 multiple parents；
- 不允许 directed cycle。

Tree 是 DAG 的严格特例。

### 15.3 Faceted Model（分面模型）

适用：

- 同一对象需要多个独立 Dimension / Facet 描述；
- 各 Facet 回答不同问题。

例：

```text
Premise Architecture

Locus
Operation
Relative Effect
```

### 15.4 Labeled Graph（带标签关系图）

适用：

- 同一知识区域混合多种 Relation Type；
- 需要保留 edge semantics（边语义）。

例：

```text
重生 → ENABLES → 信息优势
角色资产抽取 → PART_OF → 影视生产工作流
Premise Analysis → PRECEDES → Plot Analysis
```

### 15.5 Representation Decision

```text
单一层级 + 单父 → Tree
单一层级 + 多父 → DAG
多个独立描述轴 → Faceted Model
多种 Relation Type 混合 → Labeled Graph
```

大型知识系统可以是 Labeled Graph，其中局部子图分别投影为 Tree、DAG、Facet 或流程链。

## 16. Current-node Localization（当前节点定位）

推荐模板：

```text
Current Node:
Node Type:

Parent:
Relation to Parent:

Same-axis Siblings:
Children / Narrower:

Orthogonal Facets:

Upstream:
Downstream:

Unknowns:
Conflicts:
```

### 16.1 Parent 必须附 Relation Type

```text
Current Node: Advantage
Node Type: Value
Parent: Relative Effect
Relation to Parent: VALUE_OF
```

Parent / Child 是位置词；Relation Type 才定义语义。

### 16.2 Orthogonal Facets（正交分面）

与当前节点相关，但属于其他独立描述轴的 Dimension。

不得误当 siblings。

### 16.3 Upstream / Downstream

- **Upstream**：来源、前置条件、输入、先行机制、约束来源；
- **Downstream**：结果、后果、输出、后续机制。

```text
重生 → ENABLES → 信息优势
```

重生是信息优势的 upstream mechanism，不是其 Parent。

## 17. Unknown / Conflict States（未确定 / 冲突状态）

| State | 定义 |
|---|---|
| **UNKNOWN** | 当前证据不足，无法可靠判断 Relation Type |
| **CONFLICT** | 已有结构声明互相不兼容 |
| **MULTIPLE_CANDIDATES** | 存在多个合理候选关系，尚未排除 |
| **UNRESOLVED** | 问题已识别，但当前暂未解决 |

### 17.1 常见 Conflict

- **Relation Conflict**：同一节点对被声明为不兼容关系；
- **Axis Conflict**：不同 Facet 被误当成同轴 Values；
- **Cycle Conflict**：不同概念形成 hierarchy cycle；
- **Granularity Conflict**：同一比较层混入显著不同粒度的节点。

**规则：** 未确定关系保留状态，不为了图完整而伪造边。

## 18. Minimal Decision Protocol（最小判定协议）

```text
1. 明确 Modeling Purpose
2. 提取 Candidate Nodes
3. 给 Nodes 定型
4. 给 Edges 定型
5. 检查 Siblings / Axis
6. 检查 Partition Claim
7. 检查 Partial Order / Cycle / Multiple Parents
8. 选择 Tree / DAG / Faceted Model / Labeled Graph
9. 定位 Current Node（如需要）
10. 标记 Unknown / Conflict
```

完成标准：

- 没有无标签的“父子”边承担多种语义；
- 同级节点通过 criterion / type / relation 检查；
- 不把不同 Facet 平铺成 siblings；
- 不把 Upstream / Downstream 误写成 Parent / Child；
- 多父结构不用 Tree 强行表达；
- 可推导祖先边不重复堆叠；
- 不能确认的关系显式标记为 UNKNOWN / CONFLICT，而不是猜测。
