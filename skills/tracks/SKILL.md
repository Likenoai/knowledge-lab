# Tracks｜研究路线总览

短口令：**看路线**。

用于恢复 **Research / Work Tracks（研究与工作线路）** 的当前进度，而不是把所有知识文件列成目录。默认只读，不因查看路线而自行改变研究结论或文件状态。

## Context pointers（单一事实来源）

按请求范围读取已有资料，**不在本 Skill 内复制静态线路名和进度**：

- 仓库根部 `README.md`：研究分支入口。
- `INTERACTION_STATE.md`：当前启用的交互工作规则、状态入口。
- `research/<topic>/`：过程态记录、阶段结论、暂停点及后继链接。
- `principles/认知交互原则注册表.md`：工作原则（**Working Principle 不等于 Active Track**）。
- `frameworks/cognitive-augmentation/认知外化与状态更新闭环_执行协议.md`：必要时使用 CI-001 的回链和状态协调标准。
- 用户在**当前对话**中显式给出的启动、暂停、收束和优先级变化。

有 GitHub 访问时，优先实际读取最新文件；源文件缺失/不可访问时标明来源限制。不要凭上一轮口头摘要冒充仓库实时状态。

## Scope / triggers（输入）

- `看路线`：当前对话对应的**正在研究的体系**及直接相关分支；突出焦点、平行线路与阶段状态。
- `看全部路线` / `tracks 全部`：跨整个 `knowledge-lab` 搜索有依据的研究/工作线路，明确范围并按主题分组。
- `看进行中路线`：仅明确活跃及正进行运行验证的线路；暂停项可汇总数量。
- `看路线：<主题>`：该体系的研究线路及子线路。
- `看路线：下一步`：只展示可执行的下一节点及前置依赖。

`@tracks` 可以作为用户自行安装/加载 Skill 后的显式入口；仅保存到 GitHub 不代表 ChatGPT 当前会话自动注册了该 Skill。自然语言口令与用户明确请求同样有效。

## Process（执行流程）

1. **界定范围**：识别本轮研究体系，必要时区分跨项目工作线与同一体系内部子线，不把“理论层级”误当成“工作状态”。
2. **恢复来源**：先读当前入口，再追随过程日志、阶段快照的“updated in / superseded by / next”链接；如果有新旧冲突，以有依据的后继状态为当前工作判断，保留矛盾提示。
3. **识别线路**：一条路线至少具有独立的研究目标/问题及可定位的工作记录或用户明确指定的当前任务；文件夹、概念名称、Skill、工作原则本身都不自动构成研究路线。
4. **状态判定**：以文件中的明示状态和当前对话的明确决策为依据。目录存在、最后修改时间较近、Working Model 或 Working Principle 标签**不能单独证明 Active**。用以下标签：
   - `进行中`：正在做实质研究/执行。
   - `应用验证中`：规则/框架已建立，仍需真实使用验证。
   - `阶段完成`：本阶段结论/交付已完成，但不是整个主题永久结束。
   - `暂停`：有明确暂停决定且尚无被证实的后继重启。
   - `受阻`：有明确外部依赖或阻塞。
   - `状态待确认`：证据不足或相互冲突，不推断为进行中。
5. **核对阶段进度**：逐条回答“研究目标 / 目前完成了什么 / 当前卡在哪 / 下一步动作 / 是否还有待验证”。对于“结束了吗”，把**文档完成、当前阶段完成、复用验证通过、整条研究关闭**四者分开。
6. **展示结构**：默认先给总量与最活跃焦点，再给按主题分组的简表；区分父线路与子线路，不重复计数。每行包含 **线路、状态、当前停点、下一步**。用源文件链接让用户直达。
7. **推荐后续焦点**：只提供一个最有价值的下一节点和依据；如果用户只要概览，则不额外推动新研究。不可把建议伪装为用户已有承诺。
8. **仅在显式要求更新时写回**：若用户要求同步路线状态、重启、暂停或持久化，才遵循 CI-001 做 Impact Check → Reconcile → Write → Verify。普通“看路线”是只读，发现过时状态时说明冲突并建议同步，不暗中修改仓库。

## Default output（默认输出）

```text
研究路线总览｜范围：[当前主题 / 全库]｜核对时间：[日期]

焦点：[当前最明确活跃线路]
进度：进行中 X｜应用验证中 Y｜阶段完成 Z｜暂停 W｜待确认 V
（统计的是同一层级的线路；子线路不重复计入父项）

| 路线 | 状态 | 到了哪里 | 下一步 |
| ... | ... | ... | ... |

当前建议继续：[节点]，理由：[一句话]
状态冲突/来源限制：[只有确实存在时]
```

简洁优先。用户要求“图”“路线图”时才使用合适的图形表现；不把路线的状态表硬画成有歧义的 DAG。

## Boundary（禁止与停点）

- **不要混用**：研究路线 vs 知识结构；Running Track vs Working Principle；阶段完成 vs 全部结束。
- 不编造进度百分比、截止日期、优先级或自动更新能力。
- 不默认创建独立的动态状态数据库，避免形成第二个会过时的 Source of Truth。
- 不用每次都扫描整个仓库；默认先围绕当前体系查最少充分来源。
- 用户明确要求更新时，先检查旧文件是否已有当前状态；不能只新增孤立研究快照。
- 不知道的状态写 `待确认`，不强行“补全地图”。

## Completion criteria（完成判准）

用户看完可以准确回答：

1. **目前在推进哪一条？**
2. **其他线在运行验证、阶段完成、暂停还是状态未知？**
3. **每条线走到了哪里，下一步是什么？**
4. **哪些判断已经被后续文件修订，哪些尚未通过实际验证？**

本 Skill 的结果是有来源约束的工作状态快照，不是保证仓库在后台持续同步的监控面板。
