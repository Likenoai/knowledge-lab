Knowledge Structure Mapping · Sibling Check

同级资格、单轴检查与划分声明

这一阶段解决一个非常常见的问题：为什么几个概念“都和父节点有关”，却仍然不能放成同一层？

1. Sibling（同级）不是视觉位置，而是结构声明

当你画出：

Parent ├─ A ├─ B └─ C

你实际上在暗示：A、B、C 是在同一个 criterion（划分标准）下，以相同 relation type（关系类型）连接到 Parent 的可比较节点。

2. Sibling Check 的五个核心问题

① Criterion

A / B / C 是否回答同一个分类问题？

② Node Type

A / B / C 是否是同一种 Node Type？

③ Relation Type

A / B / C 与 Parent 的边是否属于同一种 Relation Type？

④ Overlap

兄弟节点之间能否重叠？如果允许，必须明确。

⑤ Exhaustiveness

是否声称已经覆盖完整空间？如果没有，不要暗示“只有这些”。

3. Single-axis Check（单轴检查）

“同级”最重要的必要条件之一，是它们来自同一个 axis / facet（轴 / 分面）。

错误： Premise Architecture ├─ Advantage ├─ Transformation └─ Relationship 原因： Advantage → Relative Effect Transformation → Operation Relationship → Locus

三者并不是同一轴上的值，因此不能作为 siblings。

4. Node Type Check（节点类型检查）

即使语义上相关，如果节点类型不同，也要警惕伪同级。

年龄 22岁 程序员

年龄 = Dimension；22岁 = Value；程序员在“职业分类”中可作为 Class，在“人物档案”中可作为 Value。它们不能因为都描述人物就自动并列。

5. Relation Type Check（边类型检查）

Parent ├─ A [IS_A] ├─ B [PART_OF] └─ C [FACET_OF]

即使视觉上都挂在 Parent 下，三条边语义不同，也不构成规范的 sibling group。

6. Overlap（重叠）不是一定错误

有些分类要求互斥，有些允许多重归属。

例如： “用户画像标签” 可以同时是： - 新用户 - 高价值用户 - 移动端用户

这里 overlap 可能是设计目标，而不是错误。

关键不是“必须互斥”，而是：是否明确知道它们会重叠，以及这种重叠是否符合当前建模目的。

7. Partition Claim Check（划分声明检查）

如果你说“X 分为 A、B、C 三类”，这不是普通罗列，而是在做一个强声明。

严格 partition（划分）通常要求：

Pairwise Disjoint 两两不重叠 Collectively Exhaustive 合起来覆盖全集

也就是常说的“互斥 + 穷尽”。

8. Taxonomy 不一定要求严格 Partition

重要区别：

“这些是几个常见类型” ≠ “X 只能分成这几类，而且彼此完全不重叠”

知识分类可以是开放的、重叠的、非穷尽的；只有当你明确声称完整划分时，才需要承担更强的 partition 约束。

9. 一个实用的 Sibling Gate（同级门槛）

准备把 A / B / C 放成同级前： 1. 同一个问题吗？ 2. 同一种 Node Type 吗？ 3. 与 Parent 是同一种 Relation 吗？ 4. 是否允许重叠？ 5. 是否声称完整分类？ 任一项不清楚 → 暂缓并列 → 改为分面 / 图 / 未确定关系

10. 为什么这一步特别重要

很多“知识树看起来怪”的根源，不是节点名称不好，而是 sibling claim（同级声明）本身不成立。

真正的错误常常不是： “父节点选错了” 而是： “这些孩子根本不是一批孩子”
